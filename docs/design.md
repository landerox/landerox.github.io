# Design — landerox.github.io

The design system behind the site: tokens, the light and dark palettes,
typography, and the accessibility and performance contract the visual
layer has to satisfy.

Scope note — this file covers **how the site looks and behaves in the
browser**. For tooling rationale see [`decisions.md`](./decisions.md),
for repo layout see [`structure.md`](./structure.md), and for EN/ES prose
conventions see `style-guide.md` (local-only).

## 2. Token architecture

Five layers, in cascade order inside `extra.css`. Later layers consume
earlier ones; nothing reaches backwards. The two feature stylesheets load
after `extra.css` in both locale configs and consume its tokens; they do not
define independent palettes or add a preprocessing step.

| Layer | Selector                        | Holds                                        |
| :---- | :------------------------------ | :------------------------------------------- |
| 1     | `@font-face`                    | Font assets only.                            |
| 2     | `:root`                         | Scheme-agnostic primitives: motion, radii, ring. |
| 3     | `[data-md-color-scheme="default"]` | Light semantic tokens + Zensical bridge.  |
| 4     | `[data-md-color-scheme="slate"]`  | Dark semantic tokens + Zensical bridge.   |
| 5     | element/component selectors     | Consume tokens. No raw brand literals.       |

`extra.css` keeps thirteen numbered sections that follow the cascade, and its
header index lists them. Sections 1–4 are layers 1–4 and sections 5–13 make up
layer 5: 1 fonts, 2–4 tokens, 5 base
typography, 6 chrome, 7 components, 8 content pages (reading panels,
references, editorial records), 9–10 home, 11 canvas, 12 workbench, and 13
accessibility (focus ring, touch, reduced motion, forced colors, print).
Accessibility is last on purpose: its overrides must beat every section
above. Any reordering is checked by comparing every element's computed style
before and after on ten pages, in light, dark, mobile, print, forced colors
and reduced motion. Only animation timing may differ.

### Naming

- `--brand*` — the accent. Interactive, never decorative-only.
- `--surface-*` — backgrounds, ordered by elevation.
- `--ink-1|2|3` — text, 1 = headings, 2 = body, 3 = secondary/meta.
- `--hairline*` — decorative separators, no contrast obligation.
- `--border-interactive` — the boundary of a *control*; held to 3:1.
- `--border-brand` — the same obligation, drawn in the accent; only the
  secondary button uses it.
- `--target-min` — the 44px minimum touch target every control uses.
- `--scrim`, `--tooltip-*` — overlays that stay dark in both schemes.
- `--edge-highlight` / `--sheen` — elevation cues rather than colors of
  their own: a 1px top highlight folded into `--shadow-raised` and
  `--shadow-lifted`, and the top-light gradient on filled controls.
  `--control-highlight` (`-hover`) is the 1px white inset on the primary
  button, scheme-agnostic.
- `--z-ambient`, `--z-dock`, `--z-hud` — stacking layers that cross
  component boundaries (canvas, sticky tools dock, hero HUD). Layers inside
  one component's stacking context stay local integers.
- `--edge-beam` / `--edge-beam-lit` — the same top edge tinted with the
  accent, on interactive surfaces only (cards and the Technical desk); see
  [Edge beam](#edge-beam).
- `--md-*` — the bridge into Zensical's own variables. Set these rather
  than overriding the theme's selectors, so components the site does not
  style explicitly still land on-palette.

### The one brand rule

Each scheme declares the accent **once**, as three channels:

```css
[data-md-color-scheme="default"] {
  --brand-rgb: 0 112 243;
  --brand: rgb(var(--brand-rgb));
  --brand-tint: rgb(var(--brand-rgb) / 10%);
}
```

Every tint derives from `--brand-rgb`. Re-theming the site is a
two-line change: `--brand-rgb` per scheme, plus `--brand-hover` /
`--brand-ink` if the hover and text-on-page variants need separate
tuning for contrast.

### Why not `@layer`

Zensical ships its CSS unlayered. Unlayered rules always win against
layered ones, so wrapping this file in `@layer` would invert every
override in it. Ordinary specificity and source order are the mechanism
here, deliberately.

## 3. Light scheme

Base surface is a very slightly cool off-white rather than pure white,
so raised surfaces have somewhere to go. Brand tokens use an electric blue
that directly aligns with the site logo (`#0070f3`).

| Token                  | Value               | Role                     | vs page | WCAG |
| :--------------------- | :------------------ | :----------------------- | ------: | :--- |
| `--surface-page`       | `hsl(220 18% 97%)`  | Page background          |       — | —    |
| `--surface-raised`     | `hsl(0 0% 100%)`    | Cards, tables, buttons   |    1.07 | —    |
| `--surface-sunken`     | `hsl(220 16% 93%)`  | Code blocks, quotes      |    1.10 | —    |
| `--ink-1`              | `hsl(222 47% 11%)`  | Headings, `strong`       |   16.68 | AAA  |
| `--ink-2`              | `hsl(217 33% 20%)`  | Body copy                |   12.55 | AAA  |
| `--ink-3`              | `hsl(215 16% 40%)`  | Meta, tab labels         |    5.67 | AA   |
| `--brand`              | `rgb(0 112 243)`    | Fills, indicators, ring  |    4.24 | 1.4.11 |
| `--brand-ink`          | `rgb(0 80 196)`     | Prose links              |    6.65 | AA   |
| `--brand-hover`        | `rgb(0 96 215)`     | Link/button hover        |    5.36 | AA   |
| `--hairline`           | `hsl(220 14% 89%)`  | Dividers, card borders   |    1.21 | n/a  |
| `--border-interactive` | `hsl(215 16% 54%)`  | Inputs, filters, tool controls |  3.43 | 1.4.11 |
| `--border-brand`       | `rgb(0 112 243 / 85%)` | Secondary button border |   3.39 | 1.4.11 |
| `--edge-highlight`     | `hsl(0 0% 100% / 80%)` | Top edge of raised surfaces |  — | n/a  |
| `--edge-beam`          | `rgb(0 112 243 / 45%)` | Resting card edge beam |      — | n/a  |
| `--edge-beam-lit`      | `rgb(0 112 243 / 80%)` | Hovered card, dialog edge beam | — | n/a |
| `--ambient-rgb`        | `rgb(0 114 245)`    | Background canvas only   |       — | n/a  |

`--brand` draws the focus ring and tints decorative indicators, which answer to
WCAG 1.4.11's 3:1 rather than 1.4.3's 4.5:1. Text on the page uses
`--brand-ink`. `--ambient-rgb` is the one token not derived from
`--brand-rgb`; see [Ambient color is not the brand
color](#ambient-color-is-not-the-brand-color).

Filled text buttons use `--control-fill: rgb(0 72 180)` and
`--control-hover: rgb(0 58 148)` in light mode. Dark mode maps these to
`--brand` and `--brand-hover`. This keeps white button text above 4.8:1
even at the brightest stop of the 22% white sheen; the browser gate
calculates composited contrast in resting, hover and focus states.

## 4. Dark scheme

**Elevation inverts.** In light mode a recessed surface is darker than
the page; in dark mode it must be *lighter*, because recessing anything
below an already very dark background reads as a hole rather than a
panel. `--surface-sunken` is therefore a step up from `--surface-page`
here, and the naming is kept only for cross-scheme symmetry. Brand tokens
use a vivid azure blue (`#60a5fa`) matching the dark logo.

| Token                  | Value                  | Role                   | vs page | WCAG |
| :--------------------- | :--------------------- | :--------------------- | ------: | :--- |
| `--surface-page`       | `hsl(222 47% 6.5%)`    | Page background        |       — | —    |
| `--surface-raised`     | `hsl(222 35% 10.5%)`   | Cards, buttons         |    1.08 | —    |
| `--surface-sunken`     | `hsl(222 38% 8%)`      | Code blocks, quotes    |    1.03 | —    |
| `--ink-1`              | `hsl(210 40% 98%)`     | Headings, `strong`     |   18.49 | AAA  |
| `--ink-2`              | `hsl(215 20% 86%)`     | Body copy              |   13.78 | AAA  |
| `--ink-3`              | `hsl(215 16% 65%)`     | Meta, tab labels       |    7.60 | AAA  |
| `--brand`              | `rgb(96 165 250)`      | Links, fills, ring     |    7.61 | AAA  |
| `--brand-hover`        | `rgb(147 197 253)`     | Hover                  |   10.74 | AAA  |
| `--hairline`           | `hsl(217 24% 24% / 75%)` | Dividers, borders    |    1.43 | n/a  |
| `--border-interactive` | `hsl(215 20% 65% / 65%)` | Inputs, filters, tool controls | 3.78 | 1.4.11 |
| `--border-brand`       | `rgb(96 165 250 / 62%)` | Secondary button border |  3.76 | 1.4.11 |
| `--edge-highlight`     | `hsl(210 40% 98% / 8.5%)` | Top edge of raised surfaces |  — | n/a  |
| `--edge-beam`          | `rgb(96 165 250 / 45%)` | Resting card edge beam |     — | n/a  |
| `--edge-beam-lit`      | `rgb(96 165 250 / 90%)` | Hovered card, dialog edge beam | — | n/a |
| `--ambient-rgb`        | `rgb(59 130 246)`      | Background canvas only  |      — | n/a  |

### Hairlines are a step lighter than a straight inversion

The dark `--hairline` used to be `hsl(217 24% 20% / 60%)`, which
composites to 1.22:1 against the page — the same figure as the light
scheme's hairline, and the wrong lesson to take from it. A 1.2:1 line on
a light page still reads because the surfaces around it are white; on a
dark page it disappears into the fill, and cards and tables were being
defined by their fill alone. The token now composites to **1.43:1**
against the page and **1.37:1** against a raised surface, with
`--hairline-strong` at 2.08:1. These are decorative separators, so the
figures carry no WCAG obligation; they are recorded so the next
adjustment starts from a number rather than an impression.

The same reasoning produced `--edge-highlight`: a 1px line of
`hsl(210 40% 98% / 8.5%)` along the top edge of every raised surface,
folded into `--shadow-raised` and `--shadow-lifted` so cards, tables,
callouts, the page lead, the availability pill and the secondary button
all read as lit from above. It composites to 1.25:1 against the raised
surface — deliberately sub-threshold, since it is a cue and not a
boundary. The light scheme declares the same token at
`hsl(0 0% 100% / 80%)`, where it is invisible on the white surfaces;
that keeps the two blocks symmetric.

### Headings are ink, not accent

Dark-mode headings were previously `hsl(220 92% 80%)` — a light blue,
the same family as links. Contrast was fine; the *hierarchy* was not.
When headings and links share a hue, nothing on the page distinguishes
"this is a section" from "this is clickable", and the accent stops
meaning anything. Headings now use `--ink-1` in both schemes and the
accent is reserved for interactive elements. Zensical's own slate
palette makes the same choice (`h1`–`h6` at full white).

To restore blue headings, override `--ink-1` inside
[Typography](#5-typography)'s heading rules
only — not the token, which body `strong` also consumes.

## 5. Typography

### Scale

Sizes are in `em` so the whole scale keys off `.md-typeset`, matching
how Zensical expresses its own. At the current `0.85rem` base and
Zensical's 125% root, body copy is ~17px.

| Element | Size                                 | Weight | Tracking   | Computed |
| :------ | :----------------------------------- | -----: | :--------- | -------: |
| `h1`    | `clamp(1.42em, 1.26em + 0.8vw, 1.62em)` | 700 | `-0.022em` | ~24–27.5px |
| `h2`    | `clamp(1.22em, 1.14em + 0.4vw, 1.32em)` | 700 | `-0.018em` | ~21–22.4px |
| `h3`    | `1.12em`                             |    600 | `-0.012em` |    ~19px |
| `h4`    | `1em`                                |    600 | `-0.008em` |    ~17px |
| body    | `0.85rem`                            |    400 | theme      |    ~17px |

The step is ~1.23 from `h1` to `h2` and tightens toward body size —
deliberately a notch below the 30 / 24 / 19px scale that preceded it,
which read oversized against 17px copy in a docs-style layout. Heading
icons follow: the theme's `1.125em` glyph is set to `0.85em` inside
`h1`–`h3` with a numeric `vertical-align` that centres it on the cap
height, so an icon no longer outweighs the title it introduces.

Tracking tightens as size grows, which is standard for a geometric
display face. `text-wrap: balance` on headings, `pretty` on prose.

Two structural exceptions:

- **Home hero.** The landing title inside `.landing-hero` takes a fluid
  `clamp(1.55em, 1.2em + 1.1vw, 1.9em)` — ~26px on a phone, ~32px on
  desktop, the size accepted in 2026-09 — with `-0.026em` tracking. Its
  floor sits above the `h2` size, so the hierarchy cannot invert at any
  width. The greeting and role above it (`.landing-eyebrow`) share the
  kicker's `0.92rem` on `--ink-3`; see [Home landing](#home-landing).
- **Kicker.** The `**Role or name** · Area` paragraph that opens About
  matches `h1 + p:has(> strong:first-child)` and renders at `0.92rem` on
  `--ink-3` (5.67:1 light, 7.60:1 dark), with the bold lead kept on
  `--ink-1` by the `strong` rule. Collaboration opens with a page lead and
  the 404 page with ordinary prose; neither matches.

### Font provenance

All families are self-hosted. No third-party font request is made.

| Family      | Axes        | Subsets         | Source              | License   | Latin bytes |
| :---------- | :---------- | :-------------- | :------------------ | :-------- | ----------: |
| Inter       | `wght` 400–700 | latin, latin-ext | Google Fonts v20, axis limited | OFL 1.1 | 36.2 KB |
| Outfit      | `wght` 400–700 | latin, latin-ext | Google Fonts v15 | OFL 1.1   |     32.3 KB |
| MesloLGM NF | static 400 + 700 | full          | Nerd Fonts        | Apache 2.0 | 28.3 KB |

`unicode-range` keeps `latin-ext` off the critical path. No page under
`content/` currently uses a character outside the `latin` subset, so a
typical EN or ES page downloads **96.8 KB** of font data — the four
latin files, Meslo Bold included, since the header wordmark and the
mono chips render at weight 700 — and never touches the extended files.

Inter's weight axis is limited to 400–700, the range every rule and every
theme style uses (no visible Inter or Outfit text renders outside it,
checked on fifteen pages in both locales). `scripts/limit_font_weights.py`
instances the upstream files with the coverage (cmap) and names unchanged,
so no glyph can go missing: the latin file went from 48.3 KB to 36.2 KB
and latin-ext from 85.1 KB to 59.3 KB. Glyph subsetting against the real
character inventory was measured and rejected: with a safe margin it
saved 2–9 KB more and would need a coverage guard. Instancing Outfit grew
its file, so Outfit stays as shipped. Re-run the script after replacing
the Inter files with a new upstream release.

Licensing note — these are third-party assets and fall under neither of
the repo's own licenses. They keep their upstream terms; the dual-license
boundary in [Content licensing (dual-license
model)](decisions.md#16-content-licensing-dual-license-model) applies to
first-party code and content.

### Why self-hosted

Zensical requested Inter and JetBrains Mono from Google Fonts with a
render-blocking `<link>` in `<head>`, and `extra.css` added Outfit with
an `@import`, producing a three-hop critical chain:

```text
extra.css → fonts.googleapis.com/css2 → fonts.gstatic.com/…woff2
```

Each hop after the first paid DNS, TLS and connection setup on a cold
cross-origin host before a single heading could paint. Cache
partitioning (shipped in every major browser since 2020) means the old
"the visitor probably has it cached from another site" argument no
longer holds: those bytes were downloaded fresh per visitor anyway.
JetBrains Mono was requested and then never used, because
`--font-mono` resolves to MesloLGM first.

Self-hosting serves the same bytes from the already-warm origin
connection, removes the render-blocking third-party stylesheet, drops
the unused family, and makes a real `font-src 'self'` CSP possible
(see [Recommendations not yet
implemented](#10-recommendations-not-yet-implemented)).

## 6. Component rules

### Links

Prose links keep an underline. Removing it leaves color as the only
signal that text is a link, which fails WCAG 1.4.1 (Use of Color)
inside running text. The underline is set at 1px with a tinted
`text-decoration-color` and `0.18em` offset so it reads as typography
rather than as a rule.

Underlines are removed where position and container already carry the
affordance: cards, footer, headings, buttons.

### Buttons

Zensical's modern variant renders `.md-button` as a **borderless pill**.
The previous CSS set `border-color` on it, which does nothing without a
`border-style`, and forced the secondary button to a white fill — a
white pill on a near-white page, distinguishable only by an invisible
border. Both variants now declare `border: 1px solid` explicitly.

| Variant   | Fill               | Border                 | Text              |
| :-------- | :----------------- | :--------------------- | :---------------- |
| Primary   | `--control-fill`   | `--control-fill`       | `--brand-contrast` |
| Secondary | `--surface-raised` | `--border-brand`       | `--ink-2`         |

The secondary is an outline in the primary's hue (2026-10): fill against
outline separates the pair, and one hue ties them together. The label stays
`--ink-2`, so blue text remains the mark of the primary and of links, and
hover still has a color change to make. WCAG 1.4.11 asks 3:1 against
*each* adjacent background, so the figure that counts is the worse of the
two: 3.39:1 in light (against the page; 3.63:1 against the button's own
fill) and 3.48:1 in dark (against the fill; 3.76:1 against the page). The
decorative `--hairline` deliberately does not attempt this.

Both alphas are load-bearing. Light `--border-brand` drops under 3:1
against the page below 78%, dark under 3:1 against the fill below 55%.
`--border-interactive` keeps the same obligation for inputs, filters and
tool controls; its dark value `hsl(215 20% 65% / 65%)` measured 2.16:1 at
40%. Recompute after any change to these tokens or to the surfaces —
the values are not eyeballable through the alpha. The border composites over
the pill's own fill (`background-clip: border-box`), and the browser gate
measures the secondary at rest against both its fill and the page, in both
schemes.

State model (2026-09 polish):

- **Rest.** The secondary carries `--shadow-raised` at rest; without an
  elevation cue the white pill sank into the light page. The
  primary carries `--sheen` (a top-light gradient, 22% white to nothing
  in light, 15% in dark) over `--control-fill` plus a brand-tinted contact
  shadow, so it reads as a solid control rather than a flat swatch.
- **Phones (≤ 30em).** Both pills go `display: flex`, full width and
  stacked, with a `0.4em` gap standing in for the whitespace flex drops
  between icon and label. Two inline pills of different widths wrapping
  onto separate lines read as a ragged afterthought.
- **Hover / keyboard focus.** Both variants lift `-2px` and swap the
  generic gray shadow for a **brand glow** derived from `--brand-rgb`
  (35% primary, 16% secondary), matching the glow language of the
  active tab, the HUD rings and the status dot. The secondary's border
  goes from `--border-brand` to full `--brand`, its fill takes
  `--brand-tint-weak` and its label `--brand-ink`. The trigger is
  `:focus-visible`, not `:focus` — the old `:focus` selector left a
  mouse-clicked button stuck in its hover treatment until blur.
- **Active.** The pill settles back to `translateY(0)` with a subtle
  tactile scale (`scale(0.98)`) and the shadow tightens at `--dur-instant`,
  so the press reads as physical contact.

### Cards

Border, radius and lift come from tokens; feature cards use the 12px
`--radius-lg` and `1.15rem 1.25rem` inner padding. The homepage `.expertise-grid`
alone receives a `14rem` minimum, and from `60em` it is pinned to two columns
so its four cards always form a 2×2; below that it auto-fits `14rem`
columns. It no longer shares a row with the
profile HUD, which now lives in the hero grid (see [Home
landing](#home-landing)), so the float clearance it once needed is gone.
Other grids retain Modern's `16rem` auto-fit rule: the
five Projects navigation cards remain equal peers linked to distinct
destinations.

Every card grid uses a `0.75rem` gap (the theme's `.4rem` read as
tiles touching), so the homepage 2×2 and the five Projects cards share
one rhythm. Collaboration's four areas are open list items within
one shared reading panel, not individual navigation cards without destinations.

**Lab entries.** Labs has three native lifecycle tabs: 3 active, 2 completed
and 6 planned studies. Each `<div class="lab-entry" markdown>` is an open
reading block with quiet separators and a heading. Purpose, starting point,
measurements, failure tests and next evidence are explicit; the active entries
use roughly 125–145 words rather than repeat the stack inventory. No badge,
slug line, card hover or nested disclosure repeats the lifecycle state.
The native tab set and its preceding `.reading-panel-heading` share one outer
surface; individual entries do not gain their own panels. The mobile label
rules match `:has(> .tabbed-content > .tabbed-block > .lab-entry)`.
On mobile, all three tabs stay in one row; each label may wrap onto
two lines rather than moving a tab to a second row. Labels retain the native
font size and use `min-width: min-content` to keep words intact. Their padding
owns the touch area; linked anchors do not add another inset. The scoped strip
rule matches Modern's directional specificity and removes its trailing spacer.
Check text bounds as well as overflow: a strip can fit while its words break
into many tiny lines. The five Projects cards
remain appropriate navigation; long studies
do not inherit that component simply because they are grouped content.

**Icon chips.** The icon that opens a card title sits in a `1.95em`
squircle chip on `--brand-tint` with a `16%` brand border and the
`--edge-highlight` inset, on `--brand-ink` (6.22:1 light, 5.61:1 dark
against the composited chip). The title paragraph is a flex pair with a
`0.65em` gap, so a two-line title wraps in its own column beside the
chip rather than under it. On hover the chip flips to a solid `--brand`
fill with `--brand-contrast` ink (4.55:1 light, 7.61:1 dark), the
tactile counterpart of the spring pop the icon already does (`--ease-spring`).
Only the title icon qualifies — `> p:first-child > .twemoji:first-child` — so the
footer arrow stays bare, and under `forced-colors` the chip keeps a
`CanvasText` border in place of its fill.

The card body is a flex column, so homepage destination links align at
the bottom even when summaries wrap differently. The 3D tilt comes from
`--rx` / `--ry` / `--ty`, written from `features/cards.js`; each has a CSS
fallback, so cards render correctly with JavaScript disabled. The
cursor-tracked radial glare that used to accompany the tilt was removed
by owner decision (2026-09): a haze following the pointer read as a
smear rather than a light source, and the [edge beam](#edge-beam)
brightening on hover already answers the cursor.

Every home block is visible on first render. A view-timeline reveal on
below-the-fold blocks left large empty gaps in full-page and mobile
captures until the viewport crossed them, and the last one, on the
introductory prose, went with the landing rewrite: hero copy is the
likely LCP element and must never start transparent.

`backdrop-filter` was removed from cards. Blurring a translucent surface
over an animated canvas forces a GPU blur every frame, which was the
single most expensive thing on the page — and cards are the numerous
case: one blurred region per card, several per viewport. Cards are
opaque now.

The frosted treatment is kept on the header, the navigation tabs, the
availability pill and, above `76.25em`, the sidebar rail. Note what this does
**not** mean: `#neural-background` is `position: fixed` across the whole
viewport at `z-index: -1`, so it is painted behind those surfaces as well, and
their blur does recompute as particles drift underneath. The trade is accepted
deliberately, on two grounds — each is a single region rather than one per card,
and all are chrome that reads as glass by design. If the canvas ever gets a
frame-cost budget, these are the regions to measure first.

The homepage contact actions deliberately stay in normal document flow:
the hero pair and the closing pair already supply enough hierarchy, and a
full-width decorated wrapper made a small action look oversized.

The memory model separates all resident weights, the uncompressed KV cache of
full-attention layers, the fixed state of linear-attention (Gated DeltaNet)
layers and an explicit reserve in binary GiB; it is not a per-GPU sizing
guarantee. The presets are Qwen3.8-27B (27.78B dense), Qwen3.8-Flash-Next
(180B MoE, 6B active) and Qwen3.8-2.4T-A95B (2,446.18B MoE, 95B active), not
model recommendations. All three interleave one full-attention layer with
three linear ones, use a head dimension of 256 and a 262,144-token native
context; their Hugging Face `config.json` sources were reviewed on
2026-09-23. Below 16 bits the checkpoint's BF16 share stays at two bytes.
A one-line architecture summary sits under the preset select, and a narrated
list under the results derives each figure: KV per token, state per request,
the cache a plain transformer would need, resident versus active weights and
contexts beyond the native window. Architecture controls live in an optional
disclosure. Saving baseline A preserves its inputs while edits produce
comparison B, with weight, KV-cache, state, reserve and total deltas in a
component table. Lower memory does not imply better quality, throughput or
sufficient device capacity.

SQL uses a finite SELECT grammar over two clearly labelled tables with 16
fictional rows, not measured hardware results or an embedded database engine.
Dataset → question → editor provides the initial path. Separate disclosures
explain columns with units/examples and SQL with purpose/code/explanation
tables. AND/OR precedence, bounded parentheses, IN, BETWEEN, LIKE, DISTINCT,
multi-column grouping/ordering, aggregates, AS and LIMIT/OFFSET are supported.

prefixes. Editing invalidates export until the visible query matches a
successful result; copying has its own status and cannot hide a query error.

stages: FROM, optional WHERE, GROUP BY or global aggregation, SELECT, and
optional DISTINCT, ORDER BY and LIMIT. It is not a physical query plan,
EXPLAIN output or runtime profile. Editing or failure hides stale stages;
executing successfully or restoring the current result's query reveals them.

Failure Lab is an explicit local simulation: 3 arrivals per tick (12 in a
burst), 5 processing attempts, 24 queue slots, and 3 total attempts per message.
It accounts for every event as written, pending, rejected or dead-lettered.
Manual backoff waits 1s then 2s; this mode does not model jitter, duplicate
delivery, circuit breakers or network/storage behavior. Playback is opt-in,
capped at 120
ticks, and pauses when offscreen, hidden, in another tool tab or behind the
console. Navigation disposes timers, listeners and observers. Status text and
dashed borders accompany warning colors. No particles, autoplay or new palette
are needed to explain the flow.

A three-step introduction frames the order-processing analogy. Each flow
node and metric has a plain-language explanation, while a condition-specific
callout explains the outcome. Model assumptions use labelled rows; event
timestamps and descriptions align separately. Four flow nodes become a
vertical sequence on narrow screens, with arrows between the stages.

A separate policy comparison runs the same 30-second incident through two
policies: A waits 1s; B adds seeded, discrete jitter to 1s/2s backoff. The
32-bit seed defaults to 42. Three allowlisted scenarios retain identical
arrivals, capacity and queue limits for both policies. Short write failures
cover ticks 5–10; the long failure covers 5–18. The next tick recovers.
The summary and selected timeline points are derived from 31 scalar snapshots
per policy, not production measurements. Queue maxima are observed at tick end,
not within-tick high-water marks. Comparing pauses manual playback without
changing its state; changing scenario or seed clears stale comparisons.
This adds no timer, network request or persistent storage, and neither policy
is assumed to win. The three-column summary keeps both policies visible on
mobile; the five-column timeline uses a labelled, keyboard-scrollable region
with a localized horizontal-scroll hint.

The SLO worksheet keeps request-based and time-based availability separate.
Request budgets use actual traffic for a complete measured window; time
budgets use the whole window with an explicitly partial observation interval.
There is no traffic forecast or request-to-minute conversion. Targets allow
0–100% with at most six decimal places, windows span one minute to 366 days,
and request counts are integers up to 10^12. Bad observations cannot exceed
the observed total. No observations remain unknown; a 100% target leaves
burn rate undefined, not healthy or infinite.

Schema diff accepts only a flat JSON object containing `columns`, with unique,
case-sensitive ASCII names, one of eight declared types and an explicit
boolean `nullable`. Each input is limited to 32,768 characters and 200 columns;
names have at most 64 characters. Unknown keys and duplicate names are errors.
It reports additions, removals, type/nullability changes and relative order,
separating old readers consuming new records from old data meeting new
constraints. Renames appear as removal plus addition; nullable does not mean
optional presence. This is not full JSON Schema, SQL DDL or a schema registry's
compatibility guarantee. Editing invalidates the report and its copy/download
actions. Examples, native advanced help and explicit clipboard/JSON download
actions remain local; temporary download URLs are revoked after use.

The table-file planner models one append-only open-table-format table with
evenly spread data. Each commit writes at least one file per partition it
touches, split at the target size; an hourly table touches ⌈24 ÷ commits per
day⌉ hours per commit, times the buckets. Compaction leaves each partition at
max(1, ⌈partition size ÷ target⌉) files, and an unpartitioned table compacts
each bucket over the whole retention. Inputs are bounded (up to 10^6 GiB a
day, 86,400 commits, 1,024 buckets, 4,096 MiB targets and 3,650 days) and
integers where the model needs them. It flags average files below a quarter
of the target, partitions smaller than one target file and more than a
million files kept without compaction; the status line counts the findings
instead of repeating the first. Parallel writers, deletes, sort order and
snapshot expiry are named as not modeled. The 512 MiB default is Iceberg's
`write.target-file-size-bytes`.

  finishes instead of snapping back when the pointer leaves. Taps skip it,
  since the logo navigates home, and reduced motion disables it. The motion
  toggle leaves it on, as it does the HUD flip, because a hover is
  user-initiated rather than motion that starts on its own.

- **Hero wave** — the `:material-hand-wave:` in the home eyebrow is tagged
  `{ .icon-wave }` via `attr_list` in both locales and waves once for
  1.7s after entry. It then stays at its neutral frame; keeping the
  auto-starting gesture finite avoids adding continuous motion beside the
  ambient canvas and HUD.
- **Title arrival** — every other `h1` and `h2` icon springs in
  (`icon-arrive`: scale 0.4 → 1.14 → 0.96 → 1 with a small rotation)
  720ms after a 180ms delay, on every page and again on every instant
  navigation, since the swap renders new nodes. The fill mode is
  `backwards`, not `both`: once the entrance ends the animation releases
  `transform`, so the `1.12` scale / `-6°` hover nudge on the heading can
  transition normally. The wave keeps its own gesture through the
  `:not(.icon-wave)` guard.
- **Card title icon** — on card hover, a spring pop (`icon-pop`,
  overshoot then settle). The keyframes' 100% frame lands exactly on the
  static hover transform, so the animation hands off to the transition
  with no seam.
- **Card arrow** — the footer-link arrow slides `translateX(4px)` toward
  its destination instead of scaling with the title icon, which it
  previously shared a rule with.
- **Button and social icons** — a bell-ring (`icon-ring`) swinging from
  a top pivot on hover. The animation only exists while hovered, so it
  re-arms on every hover-in.

Every keyframe set ends on a neutral or steady-state transform, which is
what lets the reduced-motion block's global 1ms/1-iteration zeroing end
them at rest instead of mid-gesture. On touch (`hover: none`) the
hover-triggered gestures are disabled outright — the card resets must
mirror the hover selectors exactly (`> p > .twemoji`, `a .twemoji`),
because a shorter `li:hover .twemoji` loses to them on specificity.

### Navigation tabs

The tab bar used to carry a hardcoded navy gradient
(`#1e3a8a → #11214e`) declared once for **both** schemes. In dark mode
that reads as a brand band; in light mode it wedged a dark strip between
a translucent white header and a near-white page. The bar now takes the
header's translucent, blurred surface with a hairline (fully transparent,
`--ink-3` fell to 2.38:1 over the canvas), so it reads as an extension of
the header in both schemes, and the active tab carries a brand underline.

### Content tabs

Zensical already ships the active-tab treatment: a sliding `::before`
indicator plus a bolder, higher-contrast label. Restyling the indicator
is the entire override. This replaces twenty `:nth-child` selectors
(ten per scheme) that were drawing a *second* indicator on top of the
theme's own.

### Status and recommendation text

Labs states the lifecycle once through its native tab labels. Entries do not
repeat it with a badge or surround tool names with decorative tags.
The radar's `.reference-position` presents the recommendation in words;
selected topic buttons add a pressed state, underline and tint. These are
different meanings: a topic is not an adoption verdict.

Semantic `--state-*` inks remain useful for local-tool outcomes and reference
recommendations, paired with words rather than used as the only cue. Small
text retains the 4.5:1 contrast requirement on its actual background; check
both palettes and forced colors instead of carrying a ratio from an obsolete
chip surface into the new reading layout.

### Social cards

`scripts/social_cards.py`, called from `post_build.py`, draws a 1200×630
PNG for every indexable page and points its `og:image` and `twitter:image`
at it (`/assets/images/social/<path>.png`). The home pages keep the
hand-made `social-card.png`, and `noindex` pages (the 404s) keep the
default. Each card uses the dark palette tokens and the site's own fonts
(Outfit for the title, Inter for the section and description, Meslo for
`</>` and `landerox.com`), the [edge beam](#edge-beam) along the top and a
faint network seeded by the page path, so cards differ but stay
reproducible. The section label is the active tab, so the Spanish cards

largest size that fits two lines, or three at a smaller size, and wrap
balanced; descriptions keep two lines. A title or description character
outside Inter's `latin` range stops the build instead of drawing a missing
glyph. Forty cards take about 6 s of the build and 2.8 MB of output; nothing
is committed.

### Profile HUD

210px square, a grid item of `.landing-hero`, with a 160px coin in the middle, two
counter-rotating rings and four injected data nodes. The coin is a
`preserve-3d` box: the circular photo is its front face and one
`.hud-coin__back` disc containing four Material glyphs is its reverse.
The theme renders the glyphs from the `:material-…:` shortcodes in
`index.md`. The image selector intentionally matches
the theme's `.md-typeset` scope so its fixed height outranks modern's
`.md-typeset img { height: auto }`; a future non-square source still
crops to a circle rather than an ellipse. The side nodes reach ~108px
beyond the wrapper; its inline margins (`--hud-side: 5.75rem`) reserve that
overhang inside its own grid column, so no node can reach the copy or the
viewport edge at any width. The float this replaced (design
recommendation 3) hid the side nodes below `76.25em` and needed a stepped
right margin between `76.25em` and `88.75em` (defect 34). Now they stay
visible down to `30em`; below that `--hud-side` drops to `0` and only the
top and bottom nodes remain.

**Coin flip (owner request, 2026-09).** Hovering a data node rolls the
coin over *toward that node* and shows its glyph: cloud (top), database
(right), stacked clouds for multi-cloud (bottom), robot (left). Leaving
the nodes rolls the photo back — at rest the coin is always the face.
Three attributes on the wrapper, written by `features/hud.js`, drive the CSS:
`data-hud-flip` names the node that started the roll (absent at rest)
and selects `rotateX(±180deg)` / `rotateY(±180deg)` on `.hud-coin`, with
the same function list in every state so a retargeted transition
interpolates per axis; `data-hud-axis` (`x` or `y`) pre-rotates the back
disc on the axis of that roll so the glyph lands upright and not
mirrored, and is kept through the return roll; `data-hud-face` picks
which of the four glyphs inside the disc is opaque, and is kept too so
the glyph survives the return. The reverse is *one* disc holding all four
glyphs, not four discs: moving from one node to another swaps the glyph
in place (a `--dur-instant` crossfade) instead of rolling back through
the photo, and there is no second face that could show through the
first. The four-disc build this replaced hid the leaving disc with a
delayed `visibility` transition, and a running transition cannot be
retargeted by a later `transition-delay` change, so crossing from one
node to the next left the previous glyph visible for a whole flip
(defect 35). `backface-visibility: hidden` on the photo and the disc does
the rest. Leaving a node starts a 180ms grace before the return roll,
long enough to cross to the next node; a roll requested while the
previous one is still returning reuses its axis, so the coin never
tumbles between two axes. Nothing on `.hud-coin` may set overflow,
opacity, filter or isolation: each of them flattens the 3D context.
Touch and pen have no hover, so a tap on a node toggles its face and a
tap on the coin restores the photo; the node's hover treatment doubles as
its tap-selected state through the same attributes. Under
`prefers-reduced-motion` the global duration reset turns the roll into an
instant face swap.

Node labels are localized from `LABELS` in `features/hud.js` (they used to
be English-only on the Spanish site); `data-hud-{top,right,bottom,left}` on
`.profile-hud-wrapper` overrides a node's value per page. The nodes
are `aria-hidden` — they are decorative restatements of the prose.
The existing multi-cloud node includes `GCP · AWS · Private`; adding
private infrastructure does not introduce another floating node.
Nodes have no visible border, fill, shadow or backdrop blur at rest. Hover
and tap selection add a light brand tint, text glow and the existing lift;
the portrait remains the visual center.
Color split (owner decision, 2026-08): the lowercase labels (architect /
engineer / multi-cloud / agents) render in `--ink-1` — white on the dark
scheme — while the `strong` values keep `--brand-ink`, so each node
reads as "value: label" instead of two competing accents.

**Availability pill.** A pill injected under the photo shows the
maintainer's typical, time-based availability by wall clock in
America/Caracas (fixed UTC-4, no DST since 2016, so it is derived
arithmetically — no Intl time-zone data). It is a schedule, not a real-time
presence signal. The table lives in `statusFor()` in `features/status-core.js`,
and `scripts/features.test.mjs` checks every boundary against it.

**Two windows, deliberately different.** `collaboration.md` leads with the
overlap by region (European late mornings and afternoons, the full business
day across the Americas) and names the **05:00–22:00** window behind it; the
pill models the **08:00–20:00** core of it. The page answers *when can our
time zones overlap* — the 05:00 start is what reaches the European late
morning and the 22:00 close is what completes the Pacific business day in
winter — while the pill answers
*what is he probably doing right now*. Widening one does not widen the other,
and the `offline` state says "outside the scheduled day" rather than "outside
my working window" so the two never contradict each other in the three hours
before 08:00 or the two after 20:00.

The pill carries a **status dot and localized label**:

```text
●  Deep work · Architecture
↑  ↑
|  which state
state dot (leads, as in every chat client)
```

The dot carries **one distinct hue per state, and it is the only thing that
does**: the pill's surface stays `--surface-overlay` (its own blurred glass)
and its border stays `--hairline-strong` (`--brand` on hover)
in every state. Tinting all three surfaces meant a gold state washed
the whole badge gold, and the label met a different backdrop every hour. With
one fixed surface, `--ink-2` sits at 13.30:1 in the light scheme and
13.78:1 in the dark one, composited over the page. Both color and label
communicate the state; the label always states the same information in
words, so color is never the only cue (WCAG 1.4.1).

`statusFor()` in `features/status-core.js` evaluates hours and minutes and
returns a state (color token plus EN/ES labels and titles);
`features/status.js` writes `--status-color`:

The weekend rule is evaluated first and therefore covers all of Saturday and
Sunday, including the overnight hours. Every minute of the 1,440 resolves to
exactly one state — no gaps, no overlaps. `available` and `coffee` each own
two windows: reusing a state costs nothing, a new one costs a hue, and the
palette has none to spare.

The deep-work blue is distinct from `--brand`: the accent stays reserved for
interactive elements, so a decorative status must not borrow it. Light-scheme
colors use deeper steps and dark-scheme colors use brighter counterparts; this
keeps the 7px dot legible on both surfaces — every dot clears 4.4:1 against
the pill — even though the visible label, not the color, carries the
information.

**The magenta half of the wheel stays out of the palette — with one
exception, by owner decision (2026-09): purple for `sessions`.** No pink,
fuchsia or lilac elsewhere. The other nine hues live between 0° and 215°:
red (weekend 0°), warm (lunch 18°, coffee 27°, lab 36°, triage 64°),
green (available 142°), turquoise (reviews 175°) and blue (focus 201°,
offline 215°, the last desaturated to 19% so it reads as grey); the call
state sits alone at 273°.

**Separation is stated in CIEDE2000, not in hue degrees.** Degrees lie at 7px:
`available` and `weekend` sat 59° apart and were the second-worst pair in the
system, while `coffee` and `lab` sit 8° apart and are fine — lightness and
saturation carry that one. The floor across all 45 pairs is ΔE00 **13.61** in
the light scheme (`focus` / `offline`) and **15.57** in the dark one
(`triage` / `coffee`); the red and purple that replaced lime and red in
2026-09 clear every neighbor by 15.13 or more. Any new state has to clear
that floor against every existing one, measured — not eyeballed on a color
wheel.

Labels put the **fact first**, clearly communicating response expectations.
The `title` tooltip is **per state and written for the reader**, explaining
what the state means for them — whether to write now or wait. The dot is
decorative on purpose: the label always states the same information, so
the state tokens carry no contrast obligation. The dot's pulse and the
pill's entrance ride the same reduced-motion kill switch as everything
else. Updates align to wall-clock minute boundaries, so both 15-minute coffee
windows begin and end on time. The dot carries a radar ping
(`@keyframes status-ping`); unboxed data labels have no backdrop filter.

**Layout is derived, not measured.** The wrapper declares three tokens —
`--hud-pill-height: 1.5rem`, `--hud-gap: 0.55rem`, `--hud-gap-x: 0.8rem` —
and every offset that depends on another element's size is a `calc()` over
them. The pill has that fixed height (`line-height: 1`, no vertical
padding) and straddles the wrapper's bottom edge by exactly half of it
(`bottom: calc(var(--hud-pill-height) / -2)`); the bottom node starts at
`calc(100% + var(--hud-pill-height) / 2 + var(--hud-gap))`, so it clears
the pill by construction at every root font size (the theme scales `html`
to 137.5% above `100em` and 150% above `125em`, which is exactly where the
old `bottom: -8px` / `-48px` pixel pair overlapped). The top node hangs at
`calc(100% + var(--hud-gap))` above; the side nodes sit `--hud-gap-x`
outside. Centering rides the `translate` property so `transform` stays
free for the entrance and the hover lift, and the one shared entrance
(`hud-node-in`, offset per node through `--hud-in-x` / `--hud-in-y`) fills
`backwards`: a `forwards` fill pins `transform` after the animation ends
and the hover lift could never apply (defect 32). The wrapper reserves
`4.75rem` of bottom margin for the pill and bottom node, `3.25rem` above
for the top node and `--hud-side` on both sides from `30em`, so the
hero grid sizes its column around the whole HUD.

**Hit-testing.** The wrapper carries `z-index: 1`: its own stacking
context for the rings, coin and nodes, under the sticky header (`4`). It
was introduced when a `.scroll-reveal` stacking context painted over the
left node and took its pointer events (defect 31); that reveal is gone,
and the grid layout no longer lets another block extend under the HUD.

## 7. Motion and accessibility contract

### Motion tokens

| Token              | Value                            | Use                          |
| :----------------- | :------------------------------- | :--------------------------- |
| `--dur-instant`    | `120ms`                          | Color and opacity flips      |
| `--dur-quick`      | `220ms`                          | Hover, lift, tint            |
| `--dur-settled`    | `400ms`                          | Entrances, tilt release      |
| `--dur-flip`       | `650ms`                          | Profile HUD coin flip        |
| `--dur-wipe`       | `950ms`                          | Theme-switch circular wipe   |
| `--ease-standard`  | `cubic-bezier(0.4, 0, 0.2, 1)`   | State changes                |
| `--ease-emphasized`| `cubic-bezier(0.16, 1, 0.3, 1)`  | Anything that should feel physical |
| `--ease-spring`    | `cubic-bezier(0.175, 0.885, 0.32, 1.275)` | Tactile overshoot and spring pops |
| `--ease-decelerate`| `cubic-bezier(0, 0, 0.2, 1)`     | Looping pings that fade out (status dot) |

`transition: all` is not used anywhere — it forces the browser to watch
every animatable property, including ones that trigger layout.

### Two-state palette and compatibility

The palette switch has exactly two manual choices: light (`default`) and dark
(`slate`). There is no system-preference choice or automatic response to an OS
color-scheme change. The circular View Transitions wipe uses `--dur-wipe`;
unsupported browsers or reduced-motion preferences change the scheme without
the wipe.

`overrides/main.html` runs a compatibility bridge after the theme's storage
helpers but before its palette bootstrap. It reads only the existing
`__palette` preference for migration, maps explicit schemes to the new indices
and normalizes an old automatic or invalid value to light. The bridge adds
no key of its own. Safe wrappers around the theme's storage helpers let the
current document keep working when storage is unavailable or malformed;
other preferences are preserved or read as unset. Verify reloads, both locales,
old values and unavailable storage after a theme bump. This is palette
persistence, not storage of glossary queries or CLI input.

Both configs set `extra.scope = "/"`. The theme prefixes every stored key
with its scope, which defaults to the build's base URL, so the English and
Spanish builds used to keep separate `/.__palette` and `/es/.__palette`
entries: dark chosen on `/` was lost on `/es/` (defect 39). One scope makes
the palette and the motion choice follow the visitor across the language
switch; `just test-browser` checks both.

### Reduced motion

`prefers-reduced-motion: reduce` now covers everything, and is honored
**at runtime**: `extra.js` observes the media query, so toggling the OS
setting switches the canvas between drifting and a still frame without a
reload. The still frame is the one the motion toggle produces: the same
network, painted once and repainted only on resize, scheme change or a
return to the tab, with no animation loop and no pointer tethers. A static
image moves nothing, so the preference is met while the site keeps its
look (owner decision, 2026-09-27; it was removed entirely before).

| Effect                       | Before      | Now       |
| :--------------------------- | :---------- | :-------- |
| Ambient canvas               | disabled    | still frame |
| Theme-switch wipe            | disabled    | disabled  |
| HUD node entrances           | disabled    | disabled  |
| HUD coin flip                | n/a         | instant face swap |
| **HUD ring rotation**        | **kept spinning** | disabled |
| **Card tilt / hover lift**   | **kept**    | disabled  |
| **Button and social hover transforms** | **kept** | disabled |
| Icon micro-animations (one-shot wave, title arrival, pop, slide, ring) | n/a | disabled |
| Heading-icon hover nudge | n/a | disabled |

The two counter-rotating rings were the most motion-heavy element on the
home page and were the one thing the old `@media` block did not switch
off. The block now zeroes durations globally rather than enumerating
selectors. Important declarations are reserved for overriding theme behavior,
honoring reduced motion, enforcing hidden UI state and readable print output.

### Motion toggle

The ambient canvas, the two HUD rings and the status ping start on their
own and never stop, which WCAG 2.2.2 (Pause, Stop, Hide, Level A) asks a
page to let people pause; whether `prefers-reduced-motion` alone satisfies
it is an open Working Group question ([WCAG issue
4319](https://github.com/w3c/wcag/issues/4319)), so the site offers a
visible control as well. The canvas stays site-wide by owner decision —
the toggle pauses it, it does not scope or mask it.

`setupMotionToggle()` in `features/motion.js` injects a `.motion-toggle` button
before the palette toggle: a 44px `md-header__button` with a Lucide pause
glyph drawn as a CSS mask (play when pressed), `aria-pressed` for state and
a constant localized name ("Pause animations" / "Pausar animaciones").
Pressing it writes `__motion` through the theme's storage helpers under the
shared scope and sets `html[data-motion="paused"]`. The canvas then freezes
on one still frame (repainted on resize and on scheme change, never
animated), the rings keep their angle with `animation-play-state: paused`
and the ping is removed. Below `22.5em` five 44px header controls and the
wordmark cannot fit, so a second copy at the end of the footer meta row
takes over; both copies share one state. Reduced motion and print hide
both, since nothing then moves; under reduced motion the canvas already
shows that still frame.

### Focus

There was no `:focus-visible` styling at all. One ring now covers every
interactive surface via a `:where()` list, at
`2px` solid `--brand` with a `3px` offset — 4.24:1 (light) and 7.61:1
(dark) against the page, comfortably past the 3:1 required for focus
indicators. The list lands at (0,1,0) through `:focus-visible`, so where the
theme's polyfill class rules outrank it (`.md-typeset a`, `.md-typeset
summary`, `.md-nav__link`, `.md-pagination__link` with `.focus-visible`) a
matching selector restates the ring. The ring's `4px` corner sits in a
separate rule at zero specificity (`:where(…):where(:focus-visible)`): it
rounds the ring on bare links, while pills and rounded controls keep their
own radius. A `:has(a:focus-visible)` rule lifts the ring onto the card
so it is not clipped by the card's own `overflow: hidden`. Keyboard-scrollable
regions (terminal, glossary results, SQL and simulation tables, the memory
table and scroll-wrapped Markdown tables) share one ring drawn inside their
own edge, so the console window's `overflow: hidden` cannot clip it.
`.visually-hidden` carries text that is announced but not shown, such as the
availability pill's guidance, which otherwise lived only in a `title`.

### Other modes

- `forced-colors: active` — decorative layers (including the edge beams)
  dropped, borders handed back to `CanvasText` so Windows High Contrast
  works. Masked icons (the
  motion toggle, the external-link mark) paint with `ButtonText` /
  `LinkText`, because forced colors turn their `background-color` into
  Canvas. Pressed glossary filters get a `Highlight` outline, and the checked
  Tools tab on phones carries a transparent outline that forced colors paint.
- `print` — canvas, rings, social icons, the dock and scenario-link
  controls removed; external-link marks hidden with the screen rule's own
  selector, which a shorter one lost to on specificity; reading panels,
  reference lists and the public glossary print fully open; cards flattened,
  without their edge beam, and `break-inside: avoid`.

All forced-colors and print rules of `extra.css` live in section 13;
`decision-tools.css` keeps its own small forced-colors block.

- `color-scheme` — already set correctly by Zensical's palette CSS; not
  duplicated here.

### Theme script deferred

Zensical ends `<body>` with its bundle as a classic, parser-blocking
script. Depending on a race, the first paint waited for it to download and
run, and Lighthouse's simulated LCP on the home page swung between about
2.6 s and 3.9 s. `post_build.py` adds `defer` to that tag on every page:
document order still runs the bundle before `extra.js` (a module, deferred
too), which reads `document$`. The home page then held 0.96 performance
and a 2.5 s LCP in all five runs; long pages (glossary, Blueprints, Blog)
kept their medians and an occasional slow run, a separate effect of the
simulation, since the observed first paint stays near 0.2 s. A theme
release that changes the tag's shape fails the build rather than silently
shipping it blocking ([runbook](runbook.md#site-renders-wrong-after-a-zensical-bump)).

### Ambient canvas

Measured at 1920×1080 with the 115-node cap, per frame:

| Metric                | Before  | After   | Delta        |
| :-------------------- | ------: | ------: | :----------- |
| Proximity tests       |   6,555 |  ~1,050 | ~6× fewer    |
| Canvas draw/state calls | ~2,400 |     ~21 | ~110× fewer  |
| Links drawn           |     403 |     403 | identical    |
| Per-frame DOM reads   |       2 |       0 | eliminated   |

Two changes, no visual difference — the link set is provably identical:

1. **Uniform grid.** Cells are one connection-distance wide, so each
   node is only tested against its own cell and four forward neighbors
   instead of every other node.
2. **Batched strokes.** Line alpha is quantized into six tiers and each
   tier is emitted as one path with one `stroke()`, instead of setting
   `strokeStyle` and stroking per segment. Node circles are likewise one
   path, one `fill()`.

The color scheme and `location.pathname` were being read from the DOM
on **every frame** (~120 reads/second). The palette is now cached and
refreshed by a `MutationObserver` on the scheme attribute. Device pixel
ratio is capped at 2, so a 3× display no longer pays 9× the fill cost.
Drawing is capped at 30fps and movement uses elapsed time, so high-refresh
screens do not accelerate the effect. Background tabs pause the loop; a
missing canvas context degrades to a plain background.

### The scheme attribute lives on `<body>`

Worth stating separately because it is the least obvious thing in this
system and it silently broke two revisions of the canvas.

Zensical writes `data-md-color-scheme` — and therefore resolves every
scheme token — on **`<body>`**, not on `<html>`:

```html
<html lang="en" class="no-js">
<body dir="ltr" data-md-color-scheme="default" data-md-color-primary="indigo">
```

Two consequences, both of which cost a bug:

- `documentElement.getAttribute("data-md-color-scheme")` returns `null`
  forever, so any `isDark()` written against it is permanently false.
- `getComputedStyle(documentElement)` cannot see a custom property
  declared on `<body>` — properties inherit **down**, not up — so
  reading a scheme token off `<html>` yields an empty string.

Together those two made the ambient canvas render its light-scheme
color and light-scheme alphas in *both* themes, and made the
`MutationObserver` watching for theme switches never fire. `features/env.js`
routes every scheme-aware read through a single `paletteHost()` helper
so there is one place to be right.

`<html>` is still the correct target for the view-transition custom
properties (`--click-x`, `--click-y`, `--clip-radius`) — the transition
pseudo-elements inherit from the document root — and for `html.lang`.

Zensical owns the lifecycle of `meta[name="theme-color"]`: its palette
controller creates one meta at runtime. Since 0.0.57, and still in 0.0.65
(its templates and bundle are byte-identical to 0.0.64; checked 2026-09-26), it
serializes the translucent computed header color into an invalid ten-digit hex
value, so `syncThemeColor()` owns only the content and corrects the theme's
deferred writes to the active `--surface-page` color. Static duplicate metas are
deliberately absent. Custom scheme-aware code observes `<body>` through
`paletteHost()`. Touch devices get their own contract too: `@media (hover:
none)` neutralizes hover *transforms* (sticky-hover would freeze cards and
buttons mid-levitation after a tap), and the card tilt handler binds only when
`(hover: hover) and (pointer: fine)` matches.

### Ambient color is not the brand color

The canvas reads `--ambient-rgb`, a token deliberately kept separate
from `--brand-rgb`: `0 114 245` in light, `59 130 246` in dark. The
values sit near the brand blues but are tuned per scheme for the
canvas's own alphas (0.35–0.45 for nodes), and the decoupling stands on
its own: retheming the site's accent should not silently restyle a
background effect that was tuned by eye. `features/ambient.js` carries the same
light-scheme channels as `FALLBACK_CHANNELS` for the case where the
custom property cannot be resolved — keep the two in step.

The effect runs on **every page** at full strength in both schemes —
`opacity: 0.85`, no mask, no scroll fade. This is an explicit owner
decision, twice affirmed: an early revision that faded the canvas below
the hero was reverted, and a 2026-08 variant that confined it to the
homepage hero (page-scoped mount, vertical mask, scroll-driven fade)
was reverted the same week. The canvas is the site-wide signature;
treat any future proposal to scope or mask it as already litigated.

rather than the rendered page: accessibility sat at 0.83 on all eight
audited URLs, below the 0.90 gate, and none of the causes were visible
to the eye. Fixing them takes the audited pages to 1.00 accessibility
and 1.00 SEO in CI.

Modern also puts prohibited `aria-label` attributes on checkbox labels.
`setupHeaderButtons()` in `features/header.js` moves each header icon into a
named native button, preserving the outer label required by Modern's search
error handler and checkbox toggles. Navigation exposes `aria-expanded` and
closes with Escape; the decorative overlay has no accessible name. Controls have
44px targets. The search panel becomes inert while closed, and dismissal returns
focus to its opener. Its state follows computed pointer events and the compiled
controls/results ancestry, without relying on minified class names. Re-check
these assumptions with `just test-browser` after theme upgrades.

Modern interprets head language alternates as locale roots and requests a
`sitemap.xml` beneath each. Per-page head alternates therefore caused invalid
nested sitemap requests in production. `site_meta` keeps canonical metadata
and publishes hreflang through reciprocal XML sitemap entries instead.
`post_build.py` requires matching page sets before writing either sitemap.
The native language selector loads the equivalent page in its correct locale.
Browser tests serve the production origin from a local snapshot to detect
missing requests; Lighthouse allows zero third-party requests.

content-tab indicator described in [Component rules](#6-component-rules).
`!important` count went from 104
to 14.

written against Material for MkDocs' classic markup and variable

and reads different variables. Anything added to `extra.css` should be
checked against `site/assets/stylesheets/modern/` rather than against
Material documentation — see [Re-evaluation

## 11. Re-evaluation triggers

- **Zensical minor/major bump** — re-check [Component
  rules](#6-component-rules) against the compiled
  theme CSS in `site/assets/stylesheets/modern/`. Every override in this
  system is calibrated against specific theme rules, and most entries in
  [Defects found and fixed](#9-defects-found-and-fixed) were the theme and
  the overrides disagreeing.
  Re-check the three template overrides in `overrides/partials/` too:
  they are copies of files the theme marks "automatically generated —
  do not edit", so upstream changes to them are silent here. The
  shadow-root patch in `features/search-a11y.js` is the same kind of bet on
  upstream internals; if Zensical starts naming its own search
  controls, delete it rather than leave two labels fighting.
- **Adding a third color scheme** — the [Token
  architecture](#2-token-architecture) layer split assumes exactly
  two `[data-md-color-scheme]` blocks.
- **New table interactions or charts** — ordinary comparison and worksheet
  tables already consume shared tokens. Recheck semantics, overflow and
  keyboard access for any new table behavior. Multi-series chart colors
  would need a categorical ramp, which this system does not define.
- **Brand change** — start at [Token architecture](#2-token-architecture)'s
  "one brand rule", then re-run the
  contrast figures in [Light scheme](#3-light-scheme) and [Dark
  scheme](#4-dark-scheme). Every number in those tables is
  computed, not estimated; they must be recomputed, not adjusted.
